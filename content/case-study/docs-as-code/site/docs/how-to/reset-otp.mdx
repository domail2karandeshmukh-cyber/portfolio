# Reset a user's one-time password

<PageFacts />

When a user loses or replaces the phone that holds their authenticator, delete its one-time password (OTP) credential.
Then make the user set up a new one at their next sign-in.

## Before you start {#before-you-start}

<ConfirmIdentity />

- Sign in to the admin console with an account that can manage the users of the user's realm.
- Have the user's username or email address.
- Make sure the user has their new phone, with an authenticator app such as FreeOTP, Google Authenticator, or Microsoft Authenticator.

## Steps {#steps}

:::important Add the required action before you delete the credential
In the other order, the user can sign in with the password alone between the two actions.
Tested on Keycloak 26.8.2: with the required action added first, Keycloak asks for a code until the credential is deleted, and then asks the user to set up a new authenticator.
:::

1. In the admin console, check that the user's realm is the current realm: its name is at the top of the menu.
   Select **Users**, search for the user, and then select their username.

   <Screenshot src="/img/keycloak/01-find-user.png" alt="The Users page of the admin console. The search box is outlined in green, and the username alex.morgan is outlined and marked 1." caption="Step 1. Search for the user, and then select their username." />

2. On the **Details** tab, in **Required user actions**, select **Configure OTP**, and then select **Save**.

   <Screenshot src="/img/keycloak/07-required-action.png" alt="The Details tab of alex.morgan. Configure OTP is selected in Required user actions, and the Save button is outlined in green." caption="Step 2. Configure OTP in the user's required actions, before anything is deleted." />

3. Select the **Credentials** tab, and find the row whose type is **Otp**.
   Its user label names the device, such as *Alex's phone*.

   <Screenshot src="/img/keycloak/02-credentials.png" alt="The Credentials tab of alex.morgan, marked 1, with two rows, Password and Otp. The Otp row, labelled Alex's phone, is outlined in green and marked 2." caption="Step 3. The Otp row is the lost authenticator. Leave the Password row." />

4. In the **Otp** row, open the menu at the end of the row, and then select **Delete**.

   <Screenshot src="/img/keycloak/03-delete-menu.png" alt="The menu of the Otp row is open. Its Delete item is outlined in green." caption="Step 4. Delete, in the menu of the Otp row." />

5. In the **Delete credentials?** dialog, select **Delete**.
   Check that the **Otp** row no longer appears on the **Credentials** tab.

   <Screenshot src="/img/keycloak/04-confirm-delete.png" alt="The Delete credentials? dialog over the Credentials tab. Its red Delete button is outlined in green and numbered 1." caption="Step 5. Confirm the deletion. Cancel leaves the authenticator in place." />

6. Ask the user to sign in.
   After their password, Keycloak shows **Mobile Authenticator Setup**.
   The user scans the QR code with the authenticator app on the new phone, enters the code that the app shows, names the device, and then selects **Submit**.

   <Screenshot src="/img/keycloak/09b-setup-code.png" alt="The Mobile Authenticator Setup page that the user sees. The one-time code field, the device name field and the Submit button are outlined in green. The QR code is covered." caption="Step 6. What the user sees. The QR code is covered here because it contains the secret." />

:::note If the password may also be known to someone else
Anyone who knows the password can complete step 6 with their own phone.
If the phone was stolen with the password, also select **Update Password** in step 2, so that the user sets a new password before setting up the authenticator.
:::

## Check that it worked {#check}

On the **Credentials** tab, a new **Otp** row shows the name the user gave the new device, with today's date.

:::verified Tested on Keycloak 26.8.2
On November 28, 2026, on a local test realm, the REST commands below ran as written, and the user's next sign-in went from the password to **Mobile Authenticator Setup**.
The order of the two actions was tested by signing in between them. The console screenshots date from November 19, 2026.
:::

<Screenshot src="/img/keycloak/11-new-credential.png" alt="The Credentials tab with the new Otp row, Alex's new phone, marked" caption="The new authenticator, set up by the user." />

When the realm saves admin events, **Events** > **Admin events** lists the deletion as an `ACTION` on the user's credential, and the new required action as an `UPDATE` of the user.

## Reset many users with the admin REST API {#rest-api}

After a change to the [OTP policy](../reference/otp-policy.mdx#before-change), every user's authenticator needs a reset, and the admin console does one user at a time.
The admin REST API does the same two things in the same order: it adds **Configure OTP** to the user's required actions, and then deletes the OTP credential.

<ConfirmIdentity />

Set these variables first.
Read the password from a password manager or a prompt, so that it stays out of your shell history.

```bash title="Variables"
KC_URL=https://keycloak.example.com   # your Keycloak server
REALM=portfolio-demo                  # the user's realm
KC_ADMIN=sam.rivera                   # an administrator of the master realm
USERNAME=alex.morgan                  # the user to reset
read -rs -p "Password for $KC_ADMIN: " KC_ADMIN_PASSWORD; echo
```

1. Get an access token for the admin REST API, and find the user's ID.

   ```bash
   TOKEN=$(curl -s "$KC_URL/realms/master/protocol/openid-connect/token" \
     -d grant_type=password -d client_id=admin-cli \
     --data-urlencode "username=$KC_ADMIN" --data-urlencode "password=$KC_ADMIN_PASSWORD" | jq -r .access_token)
   USER_ID=$(curl -s -H "Authorization: Bearer $TOKEN" \
     "$KC_URL/admin/realms/$REALM/users?username=$USERNAME&exact=true" | jq -r '.[0].id')
   ```

2. Add `CONFIGURE_TOTP` to the user's required actions, before deleting anything.

   :::warning Keep the actions already there
   A `PUT` replaces the user's whole list of required actions.
   Sending `{"requiredActions": ["CONFIGURE_TOTP"]}` alone removes any action the user still has to do, such as updating their profile.
   Read the list first and add to it, as this command does.
   :::

   ```bash
   ACTIONS=$(curl -s -H "Authorization: Bearer $TOKEN" "$KC_URL/admin/realms/$REALM/users/$USER_ID" \
     | jq -c '.requiredActions + ["CONFIGURE_TOTP"] | unique')
   curl -s -o /dev/null -w '%{http_code}\n' -X PUT -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
     -d "{\"requiredActions\": $ACTIONS}" "$KC_URL/admin/realms/$REALM/users/$USER_ID"
   ```

   Keycloak answers `204`.

3. Delete each of the user's OTP credentials.
   Keycloak answers each deletion with `204`.

   ```bash
   for ID in $(curl -s -H "Authorization: Bearer $TOKEN" "$KC_URL/admin/realms/$REALM/users/$USER_ID/credentials" \
     | jq -r '.[] | select(.type == "otp") | .id'); do
     curl -s -o /dev/null -w '%{http_code}\n' -X DELETE -H "Authorization: Bearer $TOKEN" \
       "$KC_URL/admin/realms/$REALM/users/$USER_ID/credentials/$ID"
   done
   ```

4. Check the result.
   No credential of type `otp` is left, and the required actions include `CONFIGURE_TOTP`.

   ```bash
   curl -s -H "Authorization: Bearer $TOKEN" "$KC_URL/admin/realms/$REALM/users/$USER_ID/credentials" | jq -c '[.[] | .type]'
   curl -s -H "Authorization: Bearer $TOKEN" "$KC_URL/admin/realms/$REALM/users/$USER_ID" | jq -c '.requiredActions'
   ```

   ```json title="Output"
   ["password"]
   ["CONFIGURE_TOTP","UPDATE_PROFILE"]
   ```

At their next sign-in, Keycloak runs the user's required actions one after another, and asks them to set up an authenticator before they get in.
