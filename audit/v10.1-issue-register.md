# Version 10.1 issue register

What the Version 10.1 audit found on karandeshmukh.dev (production at commit `67e09a2`, Version 10), what was done about each finding, and what is still open. The audit started from the brief's recruiter journeys, then looked at the rendered pages on a desktop (1,440 px) and a phone (390 px).

Priority: **P1** stops a visitor from doing what they came for, or makes the work look less credible. **P2** costs a visitor time or attention. **P3** is polish.

## Recruiter journeys

| # | Journey | Finding | Priority | Status | Fix and evidence |
|---|---|---|---|---|---|
| 1 | A recruiter has 15 seconds | The first screen gave 45 % of its height to a headline that edits itself, and the facts were in body text below it. There was no availability line, and three stacked buttons of different widths competed for the first click. | P1 | Fixed | Who, a two-line headline ("Complex technology. Clear documentation."), the facts, availability, two primary actions (**Explore my work**, **Download CV**) and four secondary links. All of it is in the first screen at 1,440 px and 390 px. |
| 2 | A recruiter wants to email or call | The site had no email address and no phone number; the contact section offered LinkedIn only. | P1 | Fixed | Email (confirmed by Karan) in the home page's contact section, every footer, the recruiter page and a new contact page with a subject ready for six kinds of message. No phone number: Karan chose email only. |
| 3 | A hiring manager has one minute | The recruiter page was a text link on phones and absent from the desktop first screen. | P2 | Fixed | **Recruiter overview** is the first secondary link in the hero. |
| 4 | A documentation manager wants a real user guide | Every software sample documents an invented product (Ledgerly, Lattice Cloud, Fieldbook, Acme Console) or an employer's product. | P1 | Open | Phase C: documentation of real, public products. |
| 5 | An aerospace recruiter wants a publication | The ARF-1 publications are there, but the downloads list labels files by their place in a group ("Its captions (WebVTT)", "Everything below in one package"), which means nothing in a flat list. | P2 | Open | Phase G: publication sets with previews. |
| 6 | Anyone on a phone | The April button covered the second call to action on the first screen. | P2 | Fixed | On phones the button waits until the hero's actions have scrolled away. |

## Publishing

| # | Finding | Priority | Status | Fix and evidence |
|---|---|---|---|---|
| 10 | The DITA PDFs listed their code font as "Atkinson Hyperlegible Mono ExtraLight". Measured again, the glyphs were the regular (400) and bold (700) weights all along: the two static fonts made from the variable font kept its default instance's name, so both carried the same PostScript name. | P3 | Fixed | The fonts are renamed Regular and Bold, with matching style bits. The six PDFs now list `AtkinsonHyperlegibleMono-Regular` (`pdffonts`). The earlier note in this register, "a weight too thin for print", was wrong. |
| 13 | A procedure written across several sections lost its order in DITA. In the developer documentation (PDF page 6), only "Create the project" became steps; "Verify" became the result, numbered from 1 again; and "Write the configuration", "Set the environment variables" and "Deploy" came after the result. The onboarding SOP, the SSH runbook, the migration guide and the account procedure had the same fault. | P1 | Fixed | `toDita` keeps the order: each section is a step, its heading the command, its numbered list the substeps. A heading such as "Procedure" that only holds the sections leaves them as the steps, and the cases under "Investigate" stay in one step. A procedure written as one list is unchanged: 25 of the 32 documents give the same DITA as before, and the other seven are the five procedures above and two documents with variables in code. All 64 topics validate against the DITA 1.3 DTDs; `scripts/selftest.mjs` has five new checks, which fail on the old converter. |
| 14 | Variables inside code stayed as written: the PDF, the HTML5 and the scenario page showed `{{cli}} auth login` instead of `lattice auth login`. | P1 | Fixed | A variable in code takes its value. In a DITA project it is a key reference inside the code block, like everywhere else. The self-test checks every scenario document for a variable left without its value. |
| 15 | A task's prerequisites, steps, result and next steps had no labels in the PDF or the HTML5, so the prerequisites ran straight into step 1. | P2 | Fixed | DITA-OT's own labels (`args.gen.task.lbl`): "Before you begin", "Procedure", "Results", "What to do next". |
| 16 | A step's command could end a page while its code started the next one (the developer documentation, step 3). | P3 | Fixed | The theme keeps a command with what follows it. |
